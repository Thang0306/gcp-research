## Q1. Cloud Storage for production uploads and artifacts (storage classes, V4 signed URLs and resumable uploads from browsers with IAM signBlob on Cloud Run, lifecycle, versioning, retention/Bucket Lock, soft delete, locations, Pub/Sub notifications)

### Takeaway
For browser-direct uploads from Cloud Run, the production pattern is: the server signs a V4 URL with IAM `signBlob` (no key file; the runtime service account needs Token Creator on itself), or the server starts a resumable session and gives the browser only the session URI. The session URI is itself a bearer token valid for one week. For audit-grade claim storage, use retention policies + Bucket Lock / Object Retention Lock on top of the default 7-day soft delete. Bucket notifications are at-least-once and unordered, so consumers must be idempotent. Hong Kong (`asia-east2`) exists as a GCS region, but the `ASIA` multi-region excludes Hong Kong, and no Philippines region is listed.

### Cited Findings
**Signed URLs (V4)**
- Longest V4 signed URL expiration is 604,800 seconds (7 days). `X-Goog-Expires` is counted in seconds from `X-Goog-Date` — [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)
- "Anyone in possession of the signed URL can use it while it's active, regardless of whether they have a valid account." Access lasts until expiry or until the signing key is rotated — [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)
- Signed URLs work only through the XML API endpoints. `X-Goog-SignedHeaders` lists headers that every request using the URL must include (so you can bind e.g. content-type at signing time) — [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)
- The official Python samples sign with `version="v4"`, `expiration=timedelta(minutes=15)`, `method="PUT"`, `content_type="application/octet-stream"` for uploads. The sample docstring says "this method requires a service account key file" — [Signing URLs with helpers](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)
- Signing without a key uses the `iam.serviceAccounts.signBlob` permission, which is in the Service Account Token Creator role (`roles/iam.serviceAccountTokenCreator`). For a compute instance's attached service account, "the service account must be the principal for this role in order to impersonate itself" — [Signing URLs with helpers](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers)
- In Python on Cloud Run, pass `service_account_email` and `access_token` (from `google.auth.default()` then `credentials.refresh()`) to `blob.generate_signed_url(version="v4", ...)`. This needs google-cloud-storage >= 1.36.1. The SA also needs a role allowing the action (e.g. `roles/storage.objectCreator` for uploads) — [Medium: Evan Peterson, "How to generate signed URLs using python in Google Cloud Run"](https://medium.com/@evanpeterson17/how-to-generate-signed-urls-using-python-in-google-cloud-run-835ddad5366) (community source). The parameters exist in library code: [google-cloud-python commit adding service_account_email/access_token to v4 signing](https://github.com/googleapis/google-cloud-python/commit/e7105475a0d9b8b7016c2395a1f1b257bf9d4af8)
- The manual signing guide confirms IAM `signBlob` can sign without a local key — [V4 signing process with your own program](https://cloud.google.com/storage/docs/access-control/signing-urls-manually)

**Resumable uploads (browser-direct, large files)**
- "Creating signed URLs for resumable uploads is unnecessary" in most cases. The session URI "acts as an authentication token", and "PUT requests don't use any signed URLs". You *can* sign the initial `POST`, but the server can usually start the session itself. "Be sure to transmit the session URI over HTTPS when giving it to a client" — [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls)
- XML API start: `POST` with empty body and header `x-goog-resumable: start` → `201`, session URI in `Location`. JSON API: `POST ...?uploadType=resumable` — [Performing resumable uploads](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads)
- "The session URI expires after a week." You can resume as many times as needed while it is active — [Performing resumable uploads](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads)
- CORS: "If you have enabled Cross-Origin Resource Sharing, you should also include an `Origin` header in both this and subsequent upload requests" (important when the server starts the session and the browser uploads) — [Performing resumable uploads](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads)
- Chunk size must be a multiple of 256 KiB (except the last chunk); at least 8 MiB is recommended. Status check: `PUT` with `Content-Length: 0` and `Content-Range: bytes */SIZE` → `308` + `Range` header shows persisted bytes. Cancel with `DELETE` on the session URI — [Performing resumable uploads](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads)

**Storage classes**
- Standard: no minimum duration, no retrieval fee. Nearline: 30-day minimum. Coldline: 90 days. Archive: 365 days. Nearline/Coldline/Archive have retrieval fees. New zonal "Rapid" class exists for zonal buckets — [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)
- All classes are low latency with no offline retrieval. Archive data is available "within milliseconds, not hours or days" — [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)
- SLAs: Standard multi/dual-region 99.95%, region 99.9%. Nearline/Coldline/Archive multi/dual-region 99.9%, region 99.0% — [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)
- Autoclass manages class transitions automatically per bucket — [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)

**Soft delete, versioning, lifecycle**
- Soft delete default retention is 7 days for new buckets, configurable 7–90 days, or 0 to disable. Soft-deleted objects keep accruing storage charges — [Soft delete](https://docs.cloud.google.com/storage/docs/soft-delete)
- With Object Versioning, a deleted live object becomes noncurrent; a deleted noncurrent object becomes soft-deleted. Lifecycle rules do not affect soft-deleted objects, and objects deleted by lifecycle rules become soft-deleted — [Soft delete](https://docs.cloud.google.com/storage/docs/soft-delete)

**Retention policy / Bucket Lock / Object Retention Lock**
- A retention policy applies retroactively to existing and new objects. Violations fail with `403 retentionPolicyNotMet`. Max retention 3,155,760,000 s (100 years) — [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)
- "Locking a bucket's retention policy is an irreversible action." A locked policy can be increased, never reduced or removed. A locked bucket can't be deleted until all objects meet retention. Locking puts a lien on the project — [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)
- Object Retention Lock sets retention per object. If both bucket and object retention apply, the object is kept until both are satisfied. Event-based holds block deletion and reset the retention clock when released. Bucket Lock + detailed audit logging helps with FINRA, SEC, CFTC requirements — [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock)

**Locations (relevant to HK / PH)**
- Asia-Pacific regions include `ASIA-EAST1` (Taiwan), `ASIA-EAST2` (Hong Kong), `ASIA-NORTHEAST1/2/3` (Tokyo/Osaka/Seoul), `ASIA-SOUTH1/2`, `ASIA-SOUTHEAST1` (Singapore), `ASIA-SOUTHEAST2` (Jakarta), `ASIA-SOUTHEAST3` (Bangkok), `AUSTRALIA-SOUTHEAST1/2`. No Philippines/Manila region is listed — [Bucket locations](https://docs.cloud.google.com/storage/docs/locations)
- Multi-region `ASIA` = "Data centers in Asia, excluding Hong Kong and Indonesia". The only predefined Asian dual-region is `ASIA1` (Tokyo + Osaka). Configurable dual-regions in `ASIA` include Taiwan + Singapore — [Bucket locations](https://docs.cloud.google.com/storage/docs/locations)
- Turbo replication ("replication within 15 minutes") is a dual-region-only option. Default dual/multi-region replication is asynchronous, with no numeric default RPO given — [Bucket locations](https://docs.cloud.google.com/storage/docs/locations)

**Event notifications**
- Pub/Sub notification events: `OBJECT_FINALIZE`, `OBJECT_METADATA_UPDATE`, `OBJECT_DELETE`, `OBJECT_ARCHIVE` (versioned buckets only), plus `OBJECT_INITIALIZE` for zonal uploads — [Pub/Sub notifications for Cloud Storage](https://docs.cloud.google.com/storage/docs/pubsub-notifications)
- At-least-once delivery, with duplicates possible ("multiple messages, with multiple IDs, that represent the same Cloud Storage event"). Order not guaranteed. Up to 30 s for a new config to start sending. Undelivered notifications may be deleted after 7 days. No delivery-time SLA — [Pub/Sub notifications](https://docs.cloud.google.com/storage/docs/pubsub-notifications)
- Max 100 notification configs per bucket, max 10 for a specific event. Payload `JSON_API_V1` carries object metadata — [Pub/Sub notifications](https://docs.cloud.google.com/storage/docs/pubsub-notifications)
- In a Google reference architecture for insurance prior-authorization intake, uploads land in a GCS bucket, an `ingestion_service` on Cloud Run detects new files, sends them to Document AI, and writes the JSON results to Firestore. CMEK and Secret Manager are in the security section — [Automate utilization-review of insurance claims](https://docs.cloud.google.com/architecture/use-generative-ai-utilization-management)

### Inferences
- The ACE design (browser-direct signed upload sessions) matches Google's docs. In an interview, the learner should say: "server starts the resumable session (or signs the POST) with the Cloud Run SA via signBlob, binds content-type and object name, uses short expiry, returns only the session URI over HTTPS, and the bucket has CORS for the web origin." This maps to MinIO's presigned PUT / multipart upload model the learner already knows.
- Because notifications are at-least-once and unordered, any "upload finished → start OCR job" trigger must dedupe, e.g. with a Firestore doc keyed by `bucket/object#generation` created in a transaction.
- For HK data-residency needs, `asia-east2` is a valid GCS region. But because Document AI has no Hong Kong location (see Q5), the documents must leave HK for OCR. This is a compliance trade-off to raise explicitly.
- Uniform bucket-level access and CMEK were in scope, but I did not fetch their pages (see Gaps).

### Gaps
- I did not fetch the uniform bucket-level access, CMEK, or Eventarc-for-GCS pages, so I have no cited facts for them here (e.g. the 90-day window to revert UBLA). Check `docs.cloud.google.com/storage/docs/uniform-bucket-level-access` and `.../encryption/customer-managed-keys`.
- I found no official Google page showing the exact Cloud Run + Python `service_account_email`/`access_token` snippet. The Python pattern is sourced from a community post plus the library commit.
- Early-deletion charge amounts and the date soft delete became the default are not on the pages I fetched.
- No Philippines GCS region was found. I did not check whether one has been announced.

## Q2. Firestore (Native mode) for job status, counters and locks (data modeling, transactions and limits, distributed counters, hot-spotting, 500/50/5, TTL, Enterprise edition / MongoDB compatibility, cost model)

### Takeaway
Firestore transactions are serializable. Server SDKs use pessimistic locking by default on Standard edition (Enterprise defaults to optimistic). Transactions have a 270 s limit, 60 s idle timeout, 20 s lock deadline and 10 MiB request size. A single document cannot take unlimited write rate, so a single `claim_id` counter document is a contention point. Shard it, pre-allocate ID blocks, or move sequence generation to a SQL sequence. Locks should be leases (owner + expiry checked inside a transaction). TTL deletes only "typically within 24 hours", so TTL can clean up old locks but must not be used to expire them. Older facts like "1 write/sec per document" and "500 writes per batch" are no longer stated as fixed limits in current docs.

### Cited Findings
**Transactions and concurrency**
- A transaction is "any number of `get()` operations followed by any number of write operations". "Read operations must be executed before write operations". Transaction functions may run more than once, so they must not modify app state — [Transactions and batched writes](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions)
- Limits: "the 270-second time limit or the 60-second idle expiration time". Lock failure when "The transaction exceeded the lock deadline (20 seconds)". "Maximum request size of 10 MiB" — [Transactions](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions)
- Transactions fail when the client is offline. Batched writes are not retried and can run offline (mobile). Security-rules atomic operations: max 20 document access calls — [Transactions](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions)
- Firestore "guarantees serializable isolation of transactions", ordered by commit time. Reads inside a transaction do not see that transaction's own earlier writes — [Transaction serializability and isolation](https://firebase.google.com/docs/firestore/transaction-data-contention)
- Concurrency mode is a database setting: `PESSIMISTIC` (transactions lock documents they read, blocking other transactions, batched and non-transactional writes) or `OPTIMISTIC`. Standard edition defaults to pessimistic. Enterprise defaults to optimistic. Mobile/web SDKs always behave optimistically. Server client libraries (Python, Go, Java, Node.js…) follow the database mode — [Transaction serializability and isolation](https://firebase.google.com/docs/firestore/transaction-data-contention)
- Contention error after retries: "ABORTED: Too much contention on these documents. Please try again." Best practice: run server SDKs close to the database, because high-latency connections cause lock contention — [Transaction serializability and isolation](https://firebase.google.com/docs/firestore/transaction-data-contention)
- Client SDKs auto-retry transient transaction failures. With raw REST/RPC you must implement retries. Keep documents per transaction small and use a bulk writer for large writes — [Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)

**Hot-spotting and ramp-up**
- 500/50/5 rule: start "with a maximum of 500 operations per second to a new collection", then increase "by 50% every 5 minutes" — [Best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)
- Avoid monotonically increasing IDs (`Customer1`, `Customer2`…). High-rate creation with a monotonically increasing indexed field (e.g. timestamp) causes hotspots, and such a field can cap a collection at 500 writes/s. Exempt it from indexing if you don't query it. Auto-IDs are scattered and avoid hotspots. High-rate deletes can also hotspot — [Best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)
- The per-document update rate "depends highly on the workload". The current best-practices page gives no fixed per-document number — [Best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)
- Use cursors, not offsets: skipped docs still add latency and are billed as reads — [Best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)

**Distributed counters**
- "You can't update a single document at an unlimited rate." Counter = parent doc with `num_shards` + `shards` subcollection, increment a random shard. A code comment says "Each shard can support being incremented once per second". "Write throughput increases linearly with the number of shards". "The cost of reading a counter value increases linearly with the number of shards". Too many shards make reads slower and costlier. Too few cause transaction retries. A roll-up document updated at a slower cadence lets clients read one doc — [Distributed counters](https://docs.cloud.google.com/firestore/native/docs/solutions/counters)

**Limits and free tier (Standard edition)**
- Max document size 1 MiB. Max API request size 10 MiB. Max 500 field transformations per document per commit (this is the only "500" left; no total write cap per commit is listed). Max depth 20. 40,000 index entries per document. Composite indexes: 200 without billing, 1,000 with billing. Transaction 270 s / 60 s idle — [Firestore quotas and limits](https://docs.cloud.google.com/firestore/quotas)
- Free tier, applied daily (reset midnight Pacific), one database per project: 1 GiB storage, 50,000 reads, 20,000 writes, 20,000 deletes — [Firestore quotas](https://docs.cloud.google.com/firestore/quotas)

**TTL**
- Configure one TTL field per collection group (console or `gcloud firestore fields ttls update ttl_field --collection-group=... --enable-ttl`). Enablement takes ten minutes or more. The field must be a Date-and-time value (Enterprise also allows an array containing one) — [TTL policies](https://docs.cloud.google.com/firestore/native/docs/ttl)
- "Data is typically deleted within 24 hours after its expiration date". Expired docs still show in queries until deleted. TTL deletes are billed as deletes and fire snapshot listeners and Firestore triggers. Subcollections are not deleted. Exempt the TTL field from indexing to avoid hotspots — [TTL policies](https://docs.cloud.google.com/firestore/native/docs/ttl)

**Editions: Standard vs Enterprise (MongoDB compatibility)**
- Enterprise supports the MongoDB-compatibility API or Native API. Standard supports Native or Datastore API. Access mode is chosen at creation and "can't change". Enterprise has an advanced query engine (180+ stages/operators, queries with or without an index), customizable indexes (unique, dense, sparse), and text and geospatial search (Preview). Standard needs covered indexes for all queries — [Firestore editions overview](https://docs.cloud.google.com/firestore/docs/editions-overview)
- Pricing: Enterprise bills by "tranches of bytes read and written". Standard bills by number of documents read or written. Committed-use discounts are 20% (1 yr) and 40% (3 yr) for both. Doc size: Enterprise 16 MiB with MongoDB compatibility, 1 MiB with Native, Standard 1 MiB. Enterprise uses SSD, and Google claims up to 5x faster and 8x burst handling — [Editions overview](https://docs.cloud.google.com/firestore/docs/editions-overview)

**Locks / job tracking patterns**
- Firestore has no native exclusive lock API. The standard approach is a lease (owner + expiry in a doc, renew before expiry, set and checked in a transaction) — [Stack Overflow (archived 2017 answer) "Cloud Firestore document locking"](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/47026295/cloud-firestore-document-locking) (community)
- A third-party lock library (SyncGuard) implements Firestore locks with atomic transactions that check expiry and ownership, plus never-deleted fence counters for strictly increasing fencing tokens. It estimates ~5–20 ms per operation — [SyncGuard Firestore backend](https://kriasoft.com/syncguard/firestore) (third-party)
- Google's insurance utilization-review reference architecture stores Document AI JSON output and request status (`in_queue`, `in_progress`, `completed`) in a Firestore collection — [Automate utilization-review of insurance claims](https://docs.cloud.google.com/architecture/use-generative-ai-utilization-management)

### Inferences
- **ACE claim_id counter:** a sequential, gap-free ID can't be sharded (shards give a count, not a unique sequence). So one counter doc is a serialization point, and its throughput is bounded by per-document contention plus transaction retries. Mitigations: (a) pre-allocate ID blocks (e.g. +100 per transaction, then hand out locally), (b) use Cloud SQL/AlloyDB `SEQUENCE` if strict sequence matters, (c) use random/UUID IDs internally and make a human-readable number separately. At typical TPA claim volume (well below one claim/sec per market), a single counter doc is fine. That is the honest interview answer.
- **ACE double-push lock:** implement as a transaction that reads `locks/{claim_id}` and writes `{owner, expires_at, fence}` only if the lock is missing or `expires_at < now`. Also make the downstream push idempotent (idempotency key = claim_id + version). Use a TTL field only to garbage-collect stale lock docs, because TTL deletion can lag up to ~24 h.
- On Standard edition with pessimistic mode, a long-running worker that opens a transaction and does slow work (e.g. calls Document AI) inside it would hold locks and hit the 20 s lock deadline or 270 s limit. Keep transactions short: read, decide, write, commit.
- Compared with Redis (the learner's background): Firestore gives durable, serializable transactions and TTL, but much higher per-op latency and per-op billing. Redis `SET NX PX` is the closest analogue to the Firestore lease.
- Enterprise edition with MongoDB compatibility matters mostly if a team wants Mongo drivers or 16 MiB docs. For ACE-style job tracking, Standard Native mode is enough.

### Gaps
- Per-operation Firestore prices (per 100K reads/writes) were not fetched. Only the free tier and editions billing units are cited.
- The default number of transaction retries (commonly said to be 5) is not on the fetched pages.
- I found no official Google doc on a Firestore distributed-lock or Cloud Run job-status pattern. The lease pattern is sourced from community/third-party pages plus the Google reference architecture for status tracking.
- The date the "500 writes per batch/transaction" limit was removed is not on the quotas page. The page simply no longer lists it.

## Q3. BigQuery as an application backend and for analytics (DML quotas and concurrency, multi-statement transactions, Storage Write API vs INSERT DML, latency, when NOT to use it for OLTP, partitioning/clustering, cost control, BigQuery ML / vector search / remote models)

### Takeaway
BigQuery is an analytical warehouse with strict per-table DML concurrency. Only 2 mutating DML statements run at once per table, 20 queue, and the rest fail. There is also a combined DML rate of 25 statements per 10 s. Multi-statement transactions take a **table-level** lock and conflicting transactions **fail immediately** instead of queuing. Primary keys are **not enforced**, and INSERTs (and insert-only MERGEs) never conflict, so `INSERT ... WHERE NOT EXISTS` is not a safe uniqueness guarantee under concurrency. Batch writes into fewer, larger statements, stream with the Storage Write API (gRPC), and keep true OLTP state in Firestore / Cloud SQL / AlloyDB / Spanner. Docs explicitly point OLTP needs to Cloud SQL federated queries.

### Cited Findings
**DML concurrency and quotas**
- UPDATE/DELETE/MERGE: up to **2** concurrent per table, up to **20** queued (`PENDING`). Beyond that: "Too many DML statements outstanding against table..., limit is 20." Interactive DML queued > **7 hours** fails — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)
- INSERT: the first **1,500** INSERTs in any 24-hour period run immediately. After that, INSERT concurrency per table is **10**, with up to **100** queued. For more frequent inserts, use the Storage Write API (gRPC) — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language); [Quotas](https://docs.cloud.google.com/bigquery/quotas)
- Maximum DML rate (INSERT + mutating combined): **25 statements every 10 seconds**. DML statements per project per day: unlimited — [Quotas](https://docs.cloud.google.com/bigquery/quotas)
- Concurrent mutating DML conflicts only when touching the **same partition**. BigQuery retries failed statements up to 3 times. "INSERT statements don't conflict with other concurrent DML". An insert-only MERGE doesn't conflict, and MERGE with UPDATE/DELETE clauses doesn't conflict if those clauses aren't invoked at run time — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)
- Each DML statement is its own implicit transaction. "If a stored procedure or multi-statement query runs only one mutating DML statement, don't wrap it in BEGIN TRANSACTION and COMMIT TRANSACTION" — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)
- Best practices: "Avoid large numbers of individual row updates or inserts. Group DML operations". Partition if updates hit older/date-ranged data. Cluster when updates filter a narrow range or a small `IN` list (e.g. `id IN (54, 57, 60)`). "For OLTP needs, consider Cloud SQL federated queries" — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)
- Fine-grained DML (Preview): optimizes sparse mutations, but only one mutating DML at a time runs on such a table, and it is not recommended for frequently mutated partitions > 2 TB — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)
- Pricing: on-demand mutating DML is billed by bytes scanned. Capacity pricing uses QUERY slots — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)
- Other quotas: 1,500 table modifications per table per day (load/copy/query-append; DML and streaming don't count). 10,000 partitions per table. 4,000 partitions modified per job. On-demand concurrent slots 2,000 per project. Query execution limit 6 h. Queued interactive queries 1,000 — [Quotas](https://docs.cloud.google.com/bigquery/quotas)

**Multi-statement transactions**
- `BEGIN TRANSACTION … COMMIT TRANSACTION / ROLLBACK TRANSACTION`, within one query (or a session). No nesting. Auto-rollback if the query ends first. Allowed: SELECT, INSERT, UPDATE, DELETE, MERGE, TRUNCATE, and TEMP table/function DDL. No permanent DDL. `CURRENT_TIMESTAMP()` returns the transaction start time — [Multi-statement transactions](https://docs.cloud.google.com/bigquery/docs/transactions)
- Updating/deleting "acquires a table-level lock, not a partition-level lock, even on partitioned tables". One mutating transaction per table. Conflicting transactions "are not queued" and fail with "Transaction is aborted due to concurrent update against table". Locks are held until commit/rollback. SELECT, INSERT, WRITE_APPEND loads and streaming still work on a locked table — [Transactions](https://docs.cloud.google.com/bigquery/docs/transactions)
- After a concurrency failure, retry with exponential backoff, "waiting at least 60 seconds before the first retry". A failed transaction can't be retried as-is. Max 100 tables and 100,000 partition modifications per transaction. Use `DELETE ... WHERE FALSE` at the start of an insert-only transaction to take the lock — [Transactions](https://docs.cloud.google.com/bigquery/docs/transactions)

**Keys and uniqueness**
- "BigQuery doesn't enforce primary and foreign key constraints" (`PRIMARY KEY NOT ENFORCED`). The optimizer uses them for join elimination. "Queries over tables with violated constraints might return incorrect results." The page suggests an identity column for uniqueness within a column — [Primary and foreign keys](https://docs.cloud.google.com/bigquery/docs/primary-foreign-keys)

**Streaming: Storage Write API vs INSERT DML vs legacy**
- Default stream: at-least-once, data queryable immediately, multiple connections. Committed type: exactly-once only with stream offsets. Pending type: atomic commit of a batch (Create → Append → Finalize → BatchCommit). Buffered type: avoid except with Beam — [Storage Write API](https://docs.cloud.google.com/bigquery/docs/write-api)
- One connection gives "at least 1 MBps". Idle connections are closed with HTTP 409. Avoid dynamic proto generation in Python (slow) — [Storage Write API](https://docs.cloud.google.com/bigquery/docs/write-api)
- Legacy `tabledata.insertAll` is now documented as "Storage Write API (REST)" — [Use the Storage Write API (REST)](https://docs.cloud.google.com/bigquery/docs/write-api-rest)
- Rows written with the Storage Write API (REST) in the last **30 minutes** can't be modified by UPDATE/DELETE/MERGE/TRUNCATE. Rows written with the gRPC Storage Write API **can** be modified by DML. Streamed data can take up to 90 min to be available for copy — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)
- Community hands-on guides: [Xebia: BigQuery Storage Write API hands-on guide with Python and Protobuf](https://xebia.com/blog/bigquery-storage-write-api-a-hands-on-guide-with-python-and-protobuf/); [dev.to Stack Labs: 13 tricks for the new BigQuery Storage Write API in Python](https://dev.to/stack-labs/13-tricks-for-the-new-bigquery-storage-write-api-in-python-296e)

**Cost control**
- "Use the maximum bytes billed setting to limit query costs when using the on-demand pricing model". Over the limit, "the query fails without incurring a charge" (may fail on clustered tables even if actual bytes would fit). Dry-run estimates are an upper bound. "For non-clustered tables, applying a LIMIT clause … doesn't affect the amount of data that is read". First 1 TiB/month of on-demand queries is free — [BigQuery pricing](https://cloud.google.com/bigquery/pricing). **Vector search, embeddings, remote models**
- `VECTOR_SEARCH` (semantic/hybrid), `AI.SEARCH` (string query over tables with autonomous embedding generation), `AI.SIMILARITY` (small comparisons). Optional `CREATE VECTOR INDEX` gives ANN (IVF and ScaNN-based). Without an index the search is brute force — [Vector search intro](https://docs.cloud.google.com/bigquery/docs/vector-search-intro)
- `AI.EMBED` / `AI.GENERATE_EMBEDDING` with remote models: inference runs in Agent Platform (Vertex AI). Models `text-embedding-005`, `text-embedding-004`, `text-multilingual-embedding-002`, `multimodalembedding@001` retire **April 1, 2027**, and embeddings from different models are incompatible — [Vector search intro](https://docs.cloud.google.com/bigquery/docs/vector-search-intro)
- "Using an index isn't supported in Standard editions". Index builds are free below a per-org size limit. Pre-filter pruning works only on partitioned or stored columns, not clustered columns. No BI Engine acceleration — [Vector search intro](https://docs.cloud.google.com/bigquery/docs/vector-search-intro)

### Inferences
- **ACE `INSERT ... WHERE NOT EXISTS`:** because INSERTs never conflict and PKs are not enforced, two concurrent workers can both see "not exists" and both insert, giving duplicate rows. An insert-only `MERGE ... WHEN NOT MATCHED THEN INSERT` has the same race. Safe options: (1) make the writer single (one worker per claim, guarded by the Firestore lease); (2) dedupe on read with `QUALIFY ROW_NUMBER() OVER (PARTITION BY claim_id ORDER BY ts DESC) = 1`; (3) move the idempotency check to Firestore/Cloud SQL, which have real transactions/unique constraints.
- **ACE `DELETE + INSERT` in a transaction:** this takes a table-level lock. A second worker doing the same on `claim_line_decisions` fails immediately (not queued), even for a different claim or partition, and should wait at least 60 s before retrying. A single `MERGE` (no transaction wrapper) would get DML queuing and partition-level conflict detection instead. This is a strong interview talking point.
- **ACE bulk `UPDATE ... SET col = CASE id WHEN ... END WHERE id IN (...)`:** correct choice. It uses 1 of the 25-per-10s DML budget and 1 of 2 concurrent mutation slots, instead of N. With clustering on `claim_id`, it also cuts bytes scanned.
- **Latency:** BigQuery DML is a job (seconds, not milliseconds), so it should not be on the user-facing request path. Use it for append-heavy logs (`classification_log`, `audit_log`), ideally via Storage Write API default stream, and for analytics. Hot mutable state (`claim_request` status) is better in Firestore or Cloud SQL, with CDC or a periodic MERGE into BigQuery for reporting.
- `audit_log` is append-only, so it fits BigQuery well. Set `require_partition_filter` + partition by date + cluster by claim_id + `maximum_bytes_billed` on app queries.

## Q4. Cloud SQL vs AlloyDB for PostgreSQL with pgvector for RAG (AlloyDB AI, ScaNN), and connecting from Cloud Run (connectors, private IP, IAM DB auth)

### Takeaway
Both run pgvector. Cloud SQL documents HNSW plus `google_ml_integration` `embedding()` calls to Vertex AI. AlloyDB adds the `alloydb_scann` ScaNN index. Google claims up to 10x faster build, 3x less memory and 4x faster queries than HNSW, with auto-tuning and SQ8 quantization (<1–2% recall loss), but AlloyDB costs more and independent benchmarks are mixed. From Cloud Run: use the language connectors or the built-in Unix socket (Cloud SQL), or private IP via Direct VPC egress. Cap pools, because each Cloud Run instance is limited to 100 connections to Cloud SQL. Use IAM DB auth to avoid passwords.

### Cited Findings
**Cloud SQL for PostgreSQL vectors**
- Requires `google_ml_integration` (v1.2+ for Vertex AI models, 1.4.2+ for third-party/custom). `pgvector` is optional, used to store `vector` values and use operators. `embedding('MODEL@VERSION', text)` returns `real[]`, so cast it to `vector`. Pin the model version, because unpinned calls are "prone to error" — [Cloud SQL: work with vector embeddings](https://docs.cloud.google.com/sql/docs/postgres/work-with-vectors)
- Documented index: HNSW with `vector_l2_ops`, `vector_ip_ops`, `vector_cosine_ops`. `m` default 16 (range 5–48), `ef_construction` default 64. Recommends `gemini-embedding-001` — [Cloud SQL vectors](https://docs.cloud.google.com/sql/docs/postgres/work-with-vectors)

**AlloyDB AI / ScaNN**
- `CREATE EXTENSION IF NOT EXISTS alloydb_scann CASCADE;` (also installs `vector`). Distances `l2`, `dot_product`, `cosine`. Operators `<->`, `<#>`, `<=>`. Indexes can be loaded into the columnar engine — [AlloyDB: store, index, query vectors](https://docs.cloud.google.com/alloydb/docs/ai/store-index-query-vectors)
- `MODE='AUTO'` (default, `SEARCH_OPTIMIZED` or `BALANCED`), `auto_maintenance` ON for auto indexes. Manual: `num_leaves` up to 100M (PG17+) / 30M (PG16−). Quantizers: `SQ8` (default, recall loss typically < 1–2%), `AH` (Preview, ~4x more compressed), `FLAT` (≥ 99% recall). Auto indexes on tables < 10,000 rows need deferred creation (Preview) — [AlloyDB vectors](https://docs.cloud.google.com/alloydb/docs/ai/store-index-query-vectors)
- AlloyDB doesn't charge for AI function calls. Model providers bill separately — [AlloyDB vectors](https://docs.cloud.google.com/alloydb/docs/ai/store-index-query-vectors)
- Vendor claims: ScaNN index creation and filtered vector search up to 10x faster than HNSW, 3x less memory, queries up to 4x faster. AlloyDB AI "extends the open-source pgvector extension" and keeps HNSW — [AlloyDB vector search overview](https://docs.cloud.google.com/alloydb/docs/ai/vector-search-landing); deep dive: [ScaNN for AlloyDB whitepaper (PDF)](https://services.google.com/fh/files/misc/scann_for_alloydb_whitepaper.pdf)

**Choosing**
- Third-party view: Cloud SQL is the flexible default (PostgreSQL/MySQL/SQL Server, lower cost). AlloyDB is for heavy PostgreSQL workloads where Cloud SQL is not fast enough, at premium price. The 4x OLTP / 100x analytics figures are Google's own. A DoiT analysis found Cloud SQL Enterprise Plus 42% faster on complex aggregations than Enterprise, while AlloyDB handled more concurrent OLTP — [DoiT: When to use AlloyDB instead of Cloud SQL (Jan 2026)](https://www.doit.com/blog/when-to-use-alloydb-instead-of-cloud-sql-for-postgresql); [Bytebase: AlloyDB vs Cloud SQL (May 2025)](https://www.bytebase.com/blog/alloydb-vs-cloudsql/)
- Google's Architecture Center has a RAG reference architecture on AlloyDB ("RAG infrastructure using Agent Platform and AlloyDB for PostgreSQL") and one on GKE + Cloud SQL — [Gen AI reference architectures overview](https://docs.cloud.google.com/architecture/genai-overview); [AlloyDB RAG architecture](https://docs.cloud.google.com/architecture/rag-capable-gen-ai-app-using-vertex-ai); [GKE + Cloud SQL RAG](https://docs.cloud.google.com/architecture/rag-capable-gen-ai-app-using-gke). The April 6, 2026 release notes say the AlloyDB guide was revised (ingestion and evaluation moved to Cloud Run functions from Cloud Run jobs) — [Architecture Center release notes](https://docs.cloud.google.com/architecture/release-notes)

**Connecting from Cloud Run**
- Cloud SQL: Unix socket at `/cloudsql/INSTANCE_CONNECTION_NAME` (encrypted automatically; 108-char socket path limit on Linux), Cloud SQL Language Connectors (encryption + IAM authorization), or private IP via Direct VPC egress / Serverless VPC Access connector on TCP 5432. The SA needs **Cloud SQL Client** — [Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)
- "Cloud Run container instances are limited to 100 connections to a Cloud SQL database." Use a connection pool that reconnects broken connections. Managed Connection Pooling exists. The Auth Proxy uses Admin API quota ≈ 2 × instances × Cloud Run instances — [Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run)
- AlloyDB Python connector: `ip_type` "PRIVATE" (default), "PUBLIC", or "PSC". IAM auth: enable it on the instance, create an IAM DB user, then `enable_iam_auth=True`. For SA users, drop `.gserviceaccount.com` from the username — [google-cloud-alloydb-connector on PyPI](https://pypi.org/project/google-cloud-alloydb-connector/1.14.1/); [AlloyDB Language Connectors](https://docs.cloud.google.com/alloydb/docs/connect-language-connectors)
- Connector roles: `roles/alloydb.client` + `roles/serviceusage.serviceUsageConsumer`. The Cloud Run codelab also grants `roles/alloydb.databaseUser` and creates a PSC-enabled instance with `alloydb.iam_authentication=on` — [AlloyDB Language Connectors](https://docs.cloud.google.com/alloydb/docs/connect-language-connectors); [Codelab: Deploy a JavaScript application to Cloud Run with AlloyDB](https://codelabs.developers.google.com/codelabs/deploy-application-with-database/alloydb-nodejs)
- The AlloyDB connectivity guide recommends Direct VPC egress (or a Serverless VPC Access connector) for private IP, and Language Connectors or the Auth Proxy for public IP — [Choose AlloyDB connectivity](https://docs.cloud.google.com/alloydb/docs/choose-alloydb-connectivity). (The search summary flagged this page's Cloud Run private-IP advice as internally inconsistent, so re-check it.)

### Inferences
- For the learner (strong PostgreSQL + Qdrant): Cloud SQL + pgvector HNSW is "PostgreSQL as you know it". AlloyDB ScaNN is the GCP-native answer to "Qdrant-like ANN performance inside Postgres", with filtered search, auto-tuning and quantization (like Qdrant's scalar quantization).
- Interview framing: choose Cloud SQL Enterprise/Enterprise Plus for < ~a few million vectors and modest QPS. Choose AlloyDB when vectors and operational data are large, filtered vector search is hot, or the columnar engine helps analytics. Use Qdrant/Vector Search when vector scale or multi-tenancy dwarfs the relational data.
- Cloud Run autoscaling × pool size can exhaust Postgres `max_connections`. Cap `max-instances` and pool size, or use managed pooling. This is the same concern as with PgBouncer, which the learner knows.

- Official Cloud SQL page does not document IVFFlat, Enterprise Plus requirements, or ScaNN on Cloud SQL. I could not confirm whether Cloud SQL offers ScaNN in 2026.
- No official side-by-side AlloyDB vs Cloud SQL decision page was found. Comparisons come from third-party blogs.
- Cloud SQL IAM database authentication page not fetched (the connect-run page only mentions IAM-based authorization in connectors).

## Q7. Production interview questions (with short correct answers and sources)

### Takeaway
These 25 questions map directly onto ACE design choices. Each answer is short and backed by a source.

### Cited Findings
1. **Q: How does a browser upload a 200 MB claim PDF directly to GCS from a Cloud Run backend with no key file?** A: Cloud Run signs a V4 URL via IAM `signBlob` (Python: `generate_signed_url(version="v4", service_account_email=..., access_token=...)`), or starts a resumable session server-side. The SA needs `roles/iam.serviceAccountTokenCreator` on itself plus object-create permission. Max expiry is 7 days, so keep it short — [Signing with helpers](https://docs.cloud.google.com/storage/docs/access-control/signing-urls-with-helpers); [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls); [Medium Cloud Run pattern](https://medium.com/@evanpeterson17/how-to-generate-signed-urls-using-python-in-google-cloud-run-835ddad5366)
2. **Q: Signed URL vs resumable session URI: what do you hand the browser, and what are the risks?** A: The session URI is itself an auth token (PUTs use no signed URL), valid one week, so send it over HTTPS only. Include `Origin` when CORS is used. Use chunks that are multiples of 256 KiB (≥ 8 MiB). Anyone holding a signed URL can use it until expiry — [Signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls); [Resumable uploads](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads)
3. **Q: How do you make raw claim documents tamper-proof for audit?** A: Use a bucket retention policy, locked (irreversible, up to 100 years), and/or per-object Retention Lock and event-based holds. Soft delete (default 7 days, 7–90) and versioning protect against accidental deletes — [Bucket Lock](https://docs.cloud.google.com/storage/docs/bucket-lock); [Soft delete](https://docs.cloud.google.com/storage/docs/soft-delete)
4. **Q: You trigger OCR on GCS `OBJECT_FINALIZE` via Pub/Sub. What can go wrong?** A: Delivery is at-least-once with possible duplicate messages for one event, unordered, up to 30 s startup, and undelivered messages may be dropped after 7 days. Make consumers idempotent (key on object + generation) — [Pub/Sub notifications](https://docs.cloud.google.com/storage/docs/pubsub-notifications)
5. **Q: Which storage class for 7-year retained claim files that are rarely read?** A: Coldline/Archive (90/365-day minimums, retrieval fees, still millisecond access), or Autoclass. Standard for hot uploads/artifacts — [Storage classes](https://docs.cloud.google.com/storage/docs/storage-classes)
6. **Q: Can you keep HK claim data in Hong Kong end to end?** A: GCS has `asia-east2` (HK), but the `ASIA` multi-region excludes HK, and Document AI has no HK location (only `us`/`eu` fully, Singapore/Mumbai limited). OCR means cross-border processing. No Philippines region is listed — [GCS locations](https://docs.cloud.google.com/storage/docs/locations); [Document AI regions](https://docs.cloud.google.com/document-ai/docs/regions)
7. **Q: Why might a single Firestore `claim_id` counter doc become a bottleneck, and how do you fix it?** A: A single document can't be updated at unlimited rate, so contention causes retries and "ABORTED: Too much contention". Distributed counters scale writes linearly with shards (reads cost more). For unique sequential IDs, pre-allocate ranges or use a SQL sequence — [Distributed counters](https://docs.cloud.google.com/firestore/native/docs/solutions/counters); [Contention](https://firebase.google.com/docs/firestore/transaction-data-contention)
8. **Q: What is the 500/50/5 rule and why do sequential IDs hurt?** A: Start new collections at ≤ 500 ops/s and increase by 50% every 5 min. Monotonic IDs or indexed timestamps create hotspots (a collection can be capped at ~500 writes/s), so use auto-IDs and exempt sequential fields from indexes — [Best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)
9. **Q: What are the Firestore transaction limits and concurrency model?** A: Reads before writes. 270 s max, 60 s idle, 20 s lock deadline, 10 MiB request. Serializable. Standard defaults to pessimistic locks for server SDKs, Enterprise to optimistic, and mobile/web are always optimistic — [Transactions](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions); [Contention](https://firebase.google.com/docs/firestore/transaction-data-contention)
10. **Q: How do you implement a lock in Firestore to prevent double push to the payer system?** A: Use a lease doc `{owner, expires_at, fence}` written in a transaction only if absent or expired. Renew while working. Make the push idempotent. Firestore has no native lock API — [Transactions](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions); [SO lease answer](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/47026295/cloud-firestore-document-locking); [SyncGuard fencing](https://kriasoft.com/syncguard/firestore)
11. **Q: Can Firestore TTL expire your locks?** A: No. TTL deletes "typically within 24 hours" after expiry, and expired docs still appear in queries. Use TTL only for cleanup and check `expires_at` in the transaction. TTL deletes are billed and fire triggers — [TTL](https://docs.cloud.google.com/firestore/native/docs/ttl)
12. **Q: Firestore Standard vs Enterprise (MongoDB compatibility)?** A: Enterprise has an advanced query engine (180+ stages), custom/unique indexes, 16 MiB docs with Mongo API, and bills by bytes. Standard requires indexes, has 1 MiB docs, and bills per document. The mode can't be changed after creation — [Editions](https://docs.cloud.google.com/firestore/docs/editions-overview)
13. **Q: What are BigQuery's DML concurrency limits per table?** A: 2 concurrent UPDATE/DELETE/MERGE plus 20 queued (then "Too many DML statements outstanding"). INSERT: 1,500 per 24 h run immediately, then 10 concurrent and 100 queued. 25 DML statements per 10 s. Conflicts only when the same partition is touched, with up to 3 automatic retries — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language); [Quotas](https://docs.cloud.google.com/bigquery/quotas)
14. **Q: Two workers run `BEGIN; DELETE ...; INSERT ...; COMMIT;` on `claim_line_decisions` at once. What happens?** A: The transaction takes a table-level lock (even on partitioned tables). The second fails immediately with "Transaction is aborted due to concurrent update against table" and is not queued. Retry after ≥ 60 s backoff, or replace the pair with one MERGE (no wrapper) to get queuing — [Transactions](https://docs.cloud.google.com/bigquery/docs/transactions); [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language)
15. **Q: Is `INSERT ... WHERE NOT EXISTS` a safe dedupe in BigQuery?** A: Not under concurrency. INSERTs (and insert-only MERGEs) never conflict, and primary keys are not enforced, so duplicates can appear. Enforce single-writer upstream or dedupe on read — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language); [Primary/foreign keys](https://docs.cloud.google.com/bigquery/docs/primary-foreign-keys)
16. **Q: Why one bulk `UPDATE ... CASE` instead of 200 single-row UPDATEs?** A: Google says to group DML. Each statement uses the 2-concurrent/20-queue and 25-per-10s budget and is billed by bytes scanned. Clustering on the filter key reduces scanning — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language); [Quotas](https://docs.cloud.google.com/bigquery/quotas)
17. **Q: Storage Write API vs INSERT DML vs legacy streaming for logs?** A: Storage Write API (gRPC) for high-frequency ingest. Default stream is at-least-once, committed stream with offsets is exactly-once, pending stream gives an atomic batch. gRPC-written rows are immediately DML-modifiable, while "Storage Write API (REST)" (old insertAll) rows are locked for 30 min — [Write API](https://docs.cloud.google.com/bigquery/docs/write-api); [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language); [Write API REST](https://docs.cloud.google.com/bigquery/docs/write-api-rest)
18. **Q: When should you NOT use BigQuery as the app datastore, and what instead?** A: Avoid it for row-level, high-concurrency, low-latency mutations or uniqueness guarantees (DML limits, table-lock transactions, unenforced keys). Use Firestore for job state, Cloud SQL/AlloyDB for relational OLTP (Google points OLTP to Cloud SQL federated queries), and BigQuery for append/analytics — [DML](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language); [Transactions](https://docs.cloud.google.com/bigquery/docs/transactions)
19. **Q: How do you stop a runaway BigQuery query bill?** A: Set `maximum_bytes_billed` (the query fails with no charge), dry-run first (an upper-bound estimate), set custom daily quotas per user/project, and partition/cluster. LIMIT doesn't reduce bytes on non-clustered tables. Choose on-demand vs editions by workload — [Cost best practices](https://docs.cloud.google.com/bigquery/docs/best-practices-costs)
20. **Q: How does vector search work in BigQuery and what are its limits?** A: `VECTOR_SEARCH`/`AI.SEARCH` with optional vector index (IVF/ScaNN ANN, else brute force). Indexes are not supported in Standard edition. Pre-filters prune only on partitioned/stored columns. Embeddings come from remote Agent Platform models, several of which retire April 1, 2027 — [Vector search intro](https://docs.cloud.google.com/bigquery/docs/vector-search-intro)
21. **Q: Cloud SQL or AlloyDB for pgvector RAG?** A: Cloud SQL: pgvector HNSW + `embedding()`, cheaper, the familiar default. AlloyDB: ScaNN (`alloydb_scann`, auto-tuned, SQ8). Google claims up to 10x faster build, 3x less memory and 4x faster queries vs HNSW, at a premium price. Independent results are mixed — [AlloyDB vectors](https://docs.cloud.google.com/alloydb/docs/ai/store-index-query-vectors); [AlloyDB overview](https://docs.cloud.google.com/alloydb/docs/ai/vector-search-landing); [Cloud SQL vectors](https://docs.cloud.google.com/sql/docs/postgres/work-with-vectors); [DoiT](https://www.doit.com/blog/when-to-use-alloydb-instead-of-cloud-sql-for-postgresql)
22. **Q: How does Cloud Run connect securely to Cloud SQL/AlloyDB, and what limits apply?** A: Cloud SQL: Unix socket `/cloudsql/...` or language connectors (Cloud SQL Client role), or private IP via Direct VPC egress. There is a 100-connection limit per Cloud Run instance, so pool connections. AlloyDB connector defaults to private IP, supports PSC, and IAM auth via `enable_iam_auth=True` with `alloydb.client` + `serviceUsageConsumer` roles — [Cloud SQL connect-run](https://docs.cloud.google.com/sql/docs/postgres/connect-run); [AlloyDB connectors](https://docs.cloud.google.com/alloydb/docs/connect-language-connectors)
23. **Q: What are Document AI online vs batch limits?** A: Online: 15 pages (30 with `imageless_mode` from page 1) and 40 MB. Batch: up to 500 pages for OCR/Layout Parser (100 Form Parser, 200 Custom Extractor), 1 GB per file, 5,000 files per request, results in GCS — [Document AI limits](https://docs.cloud.google.com/document-ai/limits)
24. **Q: How do you detect checkboxes on LOA pages, and why only those pages?** A: Enterprise OCR v2.x premium feature `ocrConfig.premiumFeatures.enableSelectionMarkDetection` → `filled_checkbox`/`unfilled_checkbox`, mutually exclusive with Math OCR. Add-ons cost about $6/1K pages vs $1.50/1K base, so limit them to LOA pages (page selector is online-only) — [Enterprise OCR](https://docs.cloud.google.com/document-ai/docs/enterprise-document-ocr); [Pricing](https://cloud.google.com/document-ai/pricing)
25. **Q: Document AI or Gemini for claim extraction?** A: Document AI gives OCR-grounded text, layout, bounding boxes, checkbox states, confidence for HITL, and pinned versions (up to 18 months). The Layout Parser adds Gemini with fewer hallucinations (Google claim). Gemini 3+ takes up to 3,000 pages per PDF for semantic extraction. Hybrid OCR → Gemini is common. Google's insurance reference uses Document AI + Firestore + HITL before Gemini — [Enterprise OCR](https://docs.cloud.google.com/document-ai/docs/enterprise-document-ocr); [Layout parser](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk); [Gemini doc understanding](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/multimodal/document-understanding); [Utilization review architecture](https://docs.cloud.google.com/architecture/use-generative-ai-utilization-management)
